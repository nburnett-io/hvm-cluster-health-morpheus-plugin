## Next

- **Automatic freeze recovery.** Wanted, and not safe yet. A first design relied on the storage array to prove a failed host was off, and live tests showed it cannot: a hung host's sessions vanish from the array within about a minute, then it logs back in on waking and its held writes land. Only something that can stop the host proves it. The next design powers the host off through its management controller, confirms that, then acknowledges, and refuses when the controller cannot be reached. It needs a controller login on every host and real hardware to test on. Worth revisiting once HPE has answered on agent versions: if 4.0.1 fixes the wrong-node acknowledgement, little may be left for it to do.
- Optional read-only switch integration, for a trunk's allowed VLANs.
- FLT-01 groups storage findings by shared iSCSI portal, so FC clusters on one array never correlate. Add an array-identity key (target WWPN or array serial) once FC hosts exist to read one from.
- The HPE question sheet that each storage default rests on: `no_path_retry` on GFS2; the per-vendor failover windows; whether a hand-set multipath value survives the agent or voids support; the supported minimum hosts per single-site cluster. One answer each would turn a plugin judgement into a vendor rule.
- 2.0 journal-replay gap (unproven): on 7.0/dlm 4.3.0 a withdrawn node's journal may not replay until it remounts. Build no check on an unproven mechanism; confirm on a nested cluster first.

## Known limits

- For the first 15 minutes after a reload, a cluster not yet checked reads `HVM-HEALTH OK` and `reloading`. So a real problem from before the reload reads OK until its first check, and an open Web Check incident closes and opens again. A freeze is found by the watch within about 4 minutes of the load at 200 clusters, and until then reads the same. Past 15 minutes it is STALE. In the 2 minutes before the first sweep any id reads as reloading, as what is monitored is not known yet.
- After a reload, a freeze still open is reported to `Availability` as starting again, and one that ended during the reload is closed when first checked, so its end is late by up to that time.
- 200 full checks in the first few minutes after a reload are more than 20 checkers can do in one interval at the 50 s assumed, so that round ends about 11 minutes after the load. No alarm follows, and it fits the status URL's 15 minutes, with up to 30 clusters holding a silent host: at 40 the simulation runs about 10 s over. If real full checks take much longer, clusters read STALE at the end of the grace until their turn comes.
- With a host silent, the next quick check has 45 s of script time. A host that needs longer reads as ran out of time (PRB-01), with its DLM state still used, until the silent host answers or leaves.
- The freeze watch keeps a cluster's host list for 5 minutes, so a host just put in maintenance may be read until then. The read changes nothing.
- A call into the agent that never returns and ignores being interrupted holds a thread. Past its limit it stops counting against the watch's 8 readers, and up to 32 such threads are allowed; past that, the watch stops reading until a call comes back or the plugin reloads. After 2 minutes of that, PRB-04 raises its alarm and `/alive` reads STALE. Freezes then wait for the next check.
- A race for the lease can have two nodes act for one sweep, as the API has no compare-and-set: both read the row at the same moment, and each reads back its own write. The next read settles it. It costs reads and no harm: alarms are identified by check, and history is read afresh for each write.
- A row that cannot be read or written leaves every node that finds so running, each saying so in its log, which is the load of no lease at all until it can be read again. So do two nodes whose names are the same, and two whose clocks are over 3 minutes apart, which each find the other's row out of date. A node standing by that takes over for one failed read stands down on the next sweep, having started its turns again.
- A takeover is a reload. It starts up to about 4 minutes after the holder stops (the 3 minute limit, and up to a minute to the next sweep), and until the watch has read a cluster, a freeze there is not known: about 6 minutes at 200 clusters. Then the first round of checks is full and takes about 11 minutes, and clusters read reloading as they do after a load.
- A node standing by answers the status URL from the row, so it is up to about 2 minutes behind: a minute between the holder's writes, and a minute between this node's reads. With no fresh row for 5 minutes it reads STALE.
- The tab on a node standing by has only the last stored summary until someone presses Check: overall health and its time, up to 15 minutes old, and no findings. The Standards, Time and other sections wait for a check too. A check pressed there shows only on that node, raises no alarm, and is forgotten when that node takes over. The holder's next check raises what it found.
- The all-clusters page on a node standing by shows stored summaries, up to 15 minutes old, and no shared causes, as only the holder has them: FLT-01's alarm still shows them.
- Reading the status port from a stranger costs a little CPU: `/status` is kept for 5 s, and two threads answer. A request has 5 s to finish. It cannot reach a host or the database, as long as `Paging.held` stays in memory.

- Below a window about 800 px wide the columns of the wider tables get narrow, as they wrap rather than scroll. At 600 px the Findings table is still about 3 px over and scrolls that much, and it is hard to read.
- The dark theme has not been checked on a real dark setup, only on a stub page with a dark background. Status colours are mid-tones that read at about 4:1 on light or dark, as nothing here can tell which the theme is.
- The plugin's checks on a removal cannot stop someone using Morpheus's Remove directly.
- A hung unmount cannot be foreseen: nothing holds the mount when it happens. Remove safely stops there; its advice is now to wait out Morpheus's own timeout rather than rush a reboot, because the kernel's wait is bounded (about 600 s, from source) and then leaves cleanly. Rushing a reboot is the unclean departure that freezes the survivors.
- The probe's GFS2 job can add a few stuck tasks in the 2 minutes before membership changes, because DLM still reads as healthy then. It is time-boxed, and cannot be avoided without skipping GFS2 reads.
- The probe's limit holds for what can be killed. A `t` read stuck in uninterruptible sleep outside GFS2, such as `journalctl` on a dead root disk, still holds it, and the host then reads as silent. So can a reader left behind by the job.
- A check run by hand with automatic checks off raises alarms that the next daily clean-up clears, though the finding may remain.
- An alarm's message is from when it was raised, so one like MOR-03's "last 900 s ago" goes stale. So do its reach, and it can still name a host or symptom that has cleared. A symptom that appears gets into the text only while nobody has acknowledged the alarm, as raising it again would lose that. The tab has the current values.
- Plugin alarms do not reach Morpheus Monitoring > Alerts, so a change window holds nothing there: it holds the status URL's answer.
- A change window can be replaced by a new one for as long as someone keeps starting them. Each is audited.
- A VLAN test of many VLANs takes minutes: each run costs about 4 s and up to 8 s per VLAN on each uplink, plus the wait between runs.
- MOR-01 stays until Morpheus clears its own status message, which can outlast the event by a long time. That is the finding: the record is stale.
- GFS-10 reads the kernel log through `journalctl -t kernel`, so with a journal that does not persist across reboots it loses what a reboot clears.
- Tenancy relies on ownership; see docs/PERMISSIONS.md.
- The master tenant is found as tenant id 1, checked to be the master, because the plugin API cannot list tenants.
- Current results and job history are in memory. After a reload the all-clusters page shows the last stored summary, up to 15 minutes old, until the next check, and a cluster's tab shows it as a line of text.
- The master tenant cannot open a cluster another tenant owns, so all-clusters rows do not link to the tab. Their Report button works.
- A reload forgets FLT-01's correlations, and clears its alarm at the first check after, even if the clusters still have the finding. Each finding keeps its own alarm.
- A reload loses up to an hour of observed time, which then shows as unknown, never as up. A VM whose log and kernel line both have no readable time counts once while VM-06 keeps it open, and stops less than a minute apart count as one.
- A forecast is a straight line, so a step moves it for as long as the step is within the 90 days. Over 60,000 bytes, which takes dozens of datastores, the oldest samples go first and are counted.
- An availability row keeps 13 months. A cluster's rows outlive it by the retention period at most, as history does.
- A name under 3 characters is not withheld from a report by name, because it would hit ordinary words. Findings that list VMs are withheld by check regardless. A cluster's own name stays in its report, even if it contains a tenant's name.
- Over 60,000 bytes of open findings, which takes several hundred, the newest are not tracked until there is room. The report says so. Retention is fixed in code (a year, 500 per cluster), not a setting.
- The API has no sharing field for networks, so a tenant reaching an operator-owned VLAN is a warning, not critical.
- After a reload, an isolation finding on a host that is silent or cut short on its first run is not on the tab or the status URL until the host can be read, as nothing in memory holds it and it cannot be rebuilt from the stored history, which keeps no VM name. Its alarm and history entry stay meanwhile, so nothing clears, and when the host is read it counts at once and is not audited twice.
- A confirming isolation finding is a warning, so a Morpheus Web Check matching `HVM-HEALTH OK` on that cluster fires for one run. It does not reach CRITICAL. A window holds it. A confirmed failure is never held.
- A host whose VMs take longer than 12 s to read on a quick check always stops at the same place, so those further down its list wait for a full check. The cut is said in NET-12's and NET-13's text.
- Busiest VMs are a rate over about 2 s, so a burst shows or is missed by chance. The figures are per host, so STO-06's hint can name a VM on another LUN than the slow one.
- CLU-01 fails under 3 hosts even with a witness.
- An existing VM kept host-passthrough through a stop and start after the cluster's CPU model changed, so MIG-06 expects a rebuild. A nested VM cannot live-migrate while it has `migratable=off`.
- The passive VLAN check is a hint: learned addresses age out after minutes, so a quiet VLAN looks like a pruned one. It reads not checked, and only the VLAN test settles it.
- The HCI Ceph layout skips DLM and GFS2 checks and has no Ceph checks.
- The VLAN test cannot tell which bridge should carry a VLAN, only which one answered. A bridge whose uplink is not an active-backup bond (a single NIC, LACP or an Open vSwitch bond) is reported as not tested, and a VLAN on it reads as inconclusive.
- Hardware checks read through `ipmitool`, which Morpheus-built hosts do not include. With the tool present but its driver not loaded, FEN-01 reads "none" though a controller may exist.
- A name in the `autoFixClusters` setting applies to every cluster with that name, in any tenant, because names can repeat. Ids are exact.
