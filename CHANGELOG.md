# Changelog

## 0.6.0

**A signed read, for a dashboard**
- **`/v1/clusters` on the status URL port**, for a tool that signs each request with an Ed25519 key: every monitored cluster by id, with its state, whether a change window holds its paging, when it was last checked and how, its overall health, counts by status, readiness by area, and its check ids by status with their catalog names. Never a host, cluster name, tenant, VM or finding text. Anything unsigned or not signed right gets 404 `HVM-HEALTH UNKNOWN`, as a path that does not exist does. A node standing by gives each cluster's word only. The answer is plain HTTP, and a copied request can be replayed for 5 minutes. See [docs/ALERTING.md](docs/ALERTING.md).
- **Reader keys**, a new setting: the public keys of the tools that may read it, one a line, a label allowed before each. Up to 20 are used. The plugin keeps no secret.
- The all-clusters page says how many reader keys are in force, and the last read refused and why. It also says when lines are not a key, and when keys are set but the Status URL port is off. The log gives why a read was refused, at most once a minute.

**A link that opens the tab**
- **A link ending in `#hvm-cluster-health-clusterTab` opens the Cluster Health tab**, once a page, by clicking the tab's own link, as a person would. A user who cannot see the tab gets nothing.

**Fixed**
- **The status URL port no longer leaves requests open (since 0.5.0).** A request that waited too long for one of its two threads was never answered or closed, so it held a connection in the appliance's JVM: two stalled clients were enough to make every later request do so. A request now has its 5 s from when a thread takes it, up to 32 wait, and past that a connection is closed at once.

Tested live on a test appliance (Morpheus 9.1.0.1, a three-host HVM 2.0 cluster): an unsigned read of `/v1/clusters` gets 404; with a reader's key in Reader keys, the reader got each cluster's counts, check ids by status, readiness and last check within a minute, matching the tab; with the key taken out, its reads were refused again; adding and removing the key in the settings dialog kept the other settings. The tab link opens the Cluster Health tab for a user signed in to Morpheus who can see the cluster. When Morpheus asks the user to sign in first, the link's tab part is lost through the sign-in and the cluster opens on its Summary tab.

## 0.5.0

**Management controller (iDRAC, iLO) through ipmitool**
- **Management controller panel** on each host: reads the controller now, read-only, through `ipmitool` and the local driver. Status (controller and firmware, self-test, host power, power restore policy, chassis faults and intrusion, sensors ok and not, event log entries and room, watchdog), inventory (model, serial, board, board serial, part number, manufacture date, BIOS) and the controller's network (address, gateway, MAC, VLAN), with the latest 15 events. Read access is enough.
- **Reset controller**, with full access, after the host name is typed: `ipmitool mc reset cold`, which restarts the controller and never the host. Refused during a GFS2 freeze, and when the controller is not answering in the first place. Audited. It does not wait for the controller to come back: an operation holds the cluster while it runs, and a fence acknowledgement or a freeze check must never wait minutes behind a controller. Open the panel again a few minutes later.
- **Install ipmitool**, a safe-tier fix that is never automatic, from the panel or from any finding ipmitool's absence leaves unread (FEN-01, HW-01, HW-03, HW-04, HW-08). New packages only from the host's own repositories, refused if apt's simulation would upgrade or remove anything else; the lists are refreshed only when they do not offer it; needrestart is held off; the IPMI driver is loaded and set to load at boot only when it had to be loaded.
- **HW-08 Management controller healthy** (full check): FAIL when the self-test did not pass, WARN when the event log is 90% full or has overflowed. NOT CHECKED, with the install fix, when ipmitool is missing or no controller answered.
- **HW-09 No chassis or sensor faults** (full check): FAIL on a chassis fault flag (power overload, main power, power control, drive, cooling or fan), a critical or non-recoverable sensor, or a discrete sensor naming a failure, fault or IERR in its reading, as ipmitool's status column judges thresholds only. WARN on a non-critical sensor. Sensors HW-01 or HW-03 already flag are left to them. PASS only when the whole sensor list and the chassis status were read.
- **The probe asks the controller once before anything else.** A wedged controller held every ipmitool read to its limit, about 120 s, the whole full probe's budget; now one 10 s `mc info` decides whether the rest run. The event log is read with `sel elist last 40`, as a full log read whole could be cut partway and leave entries from its middle.
- The wording that Morpheus-built hosts lack ipmitool now says 1.3: 2.0 hosts ship it, and their agent polls the controller with it every minute.
- A fix can carry its own time limit; the install has 300 s, with `apt-get update` bounded at 60 s and the package lock waited on for 30 s, and the install itself never under a timeout, as a dpkg killed partway leaves the package system needing repair.

Tested live on a test appliance: the panel on three Dell R640 2.0 hosts with iDRAC; the install on two nested 1.3 hosts (new packages only, no controller found, as on a virtual machine) and its already-installed path; the reset's refusals with no typed name and with no controller. An independent review of the change found eleven issues, ten of them fixed here; the eleventh, that the package might start ipmievd, was checked on the installed hosts and it does not. HW-08 and HW-09 passed on the 2.0 hosts. A reset of a real controller, a failing self-test, a full event log and a raised fault have not been seen.

## 0.4.0

Built for one appliance running about 200 clusters and 600 hosts. Everything below comes with a simulation of that size; how a real appliance bears it is still to be measured.

**Scale, status URL and freeze watch**
- **Status URL.** Set **Status URL port** and a URL monitor or a Morpheus Web Check can read `/alive`, `/status` and `/cluster/<id>` with no login. Plain words and counts only, never a host, cluster, tenant or finding. It answers from memory, so a request never reaches a host or the database. A port that cannot be used is logged, shown on the all-clusters page and tried again; it never fails the plugin. See [docs/ALERTING.md](docs/ALERTING.md), which also states that plugin alarms do not reach Morpheus alert rules, and gives the REST calls for a Web Check and a rule per cluster.
- **Freeze watch.** Between quick checks, reads one host per cluster (`dlm_tool ls` and quorum, nothing that touches GFS2) every **Freeze watch** seconds, 60 by default, on threads of its own, and asks for a quick check ahead of the queue when it finds a freeze. It is held to **Freeze watch reads a minute**, 120 by default: with 200 clusters the interval stretches to 100 s rather than the load growing, and the tab and all-clusters page say so. A sighting is read again 15 s later before it counts, and one host reading clear only asks for a check, which reads every host. HCI Ceph clusters and hosts in maintenance are skipped.
- **Clusters checked at once** replaces 4 fixed checkers, which kept up with about 60 clusters. The default of 20 comes from the arithmetic, given in the code.
- **Checks are spread out.** A cluster's turn is set by its id, so after a reload the first checks spread across one quick interval rather than all starting at once, and full checks spread across the day rather than 200 at once a day after a restart.
- **A silent host costs less.** After a check in which a host gave no answer, the next automatic quick check has a limit of 75 s rather than 150 s.
- **PRB-04 Checks are keeping up.** One alarm on the master tenant when the most overdue cluster is over 2 intervals past its turn. Its numbers are on the all-clusters page, and `/alive` reads STALE meanwhile.
- **Alarms of a removed cluster** clear on the third sweep without it, rather than up to a day later. Never when Morpheus lists no clusters.
- **A reload does not open a Web Check incident on every cluster.** For the first 15 minutes after a load, a cluster not yet checked answers `HVM-HEALTH OK` with a second line `reloading`, and `/status` counts it under the new `reloading=N`, raising nothing. A freeze the watch holds is still CRITICAL at once. Past 15 minutes, or if the sweep stops or checks are off, an unchecked cluster is STALE as before. `/alive` is not relaxed.
- **The freeze watch reads clusters whose check is only waiting in the queue.** It skipped them, which after a reload could be most of them. It still leaves one whose check is running.
- **A freeze watch that has stopped says so.** If stuck agent calls hold all its threads, so that no read can start for 2 minutes, PRB-04 raises its alarm in its own words, `/alive` reads STALE and the all-clusters page says why. It clears when a read starts again.
- A frozen cluster with no evaluation yet is CRITICAL in `Paging.state` itself, not only by way of the status URL.

**One appliance node runs the checks**
- **A lease.** Every node used to run its own monitor, so a three-node appliance read every host three times. Now one row holds which node runs the checks, replaced on every sweep: that node alone sweeps, reads hosts for the freeze watch, raises alarms and applies automatic fixes. Another takes over once the row is over 3 minutes old. A single-node appliance pays one row replacement a minute and otherwise goes on as it did. There is no new setting.
- **Any node's status URL still answers.** The row holds what the URL says, in a few KB at 200 clusters. A node standing by answers from it, and reads STALE when it is over 5 minutes old, the limit the holder uses for its own sweep.
- **A person's check works on any node,** and shows on that node's tab. Its alarms wait for the holder's next check. A tab on a node standing by says so, and shows the last stored summary. The all-clusters page says which node holds the lease.
- **The all-clusters page reads stored summaries in one query,** not one per cluster.

**Host checks and tenant isolation**
- **Tenant isolation on every check:** NET-12 and NET-13 now run on quick checks, not only full ones. A finding counts only once two checks in a row see it, at least a minute apart, so a network being changed does not page anyone: the first sighting is a warning marked confirming. A failure writes an audit entry, naming the check and host and never the tenant. Their alarms are named `SECURITY:`. A host whose ports could not be read keeps what it last had, and a quick check on a frozen host leaves libvirt alone, as neither says the finding has gone.
- **A port read that failed no longer reads as something else:** a libvirt that did not answer was a host with no ports, and an Open vSwitch read that timed out was a port with no tag, which is a finding. Both are now not checked.
- **HST-04:** OOM kills in 24 h, a failure when the victim is a VM. **HST-05:** swap traffic over the probe's sample, not swap merely in use (`swapWarnPagesPerSec`). **HST-06, HST-07:** CPU and memory pressure from `/proc/pressure`, with CPU steal shown (`cpuPressureWarnPct`, `cpuPressureFailPct`, `memPressureWarnPct`, `memPressureFailPct`). **HST-08:** space and inodes on the host's own disks (`rootDiskWarnPct`, `rootDiskFailPct`), by named paths only, as a bare `df` blocks on a frozen GFS2. **VM-06:** a VM crashed or killed for lack of memory in 24 h.
- **Busiest VMs:** the probe samples each running VM's CPU and disk counters twice, on a full check, or on a quick one when a LUN or the kernel says I/O is waiting, and never with DLM stopped. The cluster's view holds the top five per host, for operators only and never in a report, and STO-06's hint names the busiest.
- **Host OS, kernel and network posture (full check only), all read-only and detect-and-raise, as HPE owns these settings:**
  - **PKG-04 Automatic updates cannot restart the cluster stack:** reads apt sources, the unattended-upgrades state and the needrestart config. WARN when a stock Ubuntu archive is configured, unattended-upgrades is on, and no needrestart drop-in sets list-only or names the cluster daemons: on a GFS2 member, a library update can restart corosync or dlm across the fleet inside one 06:00 window. The safe case is an HVM-sourced host whose mvm needrestart drop-in exempts the stack, and the finding says which was found.
  - **KRN-01 panic posture:** FAIL on `hung_task_panic` (a normal fence wait could panic every survivor at once); WARN on `softlockup_panic`, `kernel.panic` above 0, or `errors=panic` on a GFS2 mount. `panic_on_oops` is shown for context. Raise with HPE; the plugin changes no sysctl or mount option.
  - **KRN-02 kernel taint:** FAIL on the bad-page or oops/BUG bit, WARN on the machine-check or soft-lockup bit, from `/proc/sys/kernel/tainted`. Proprietary and out-of-tree module bits are ignored. The bit holds until reboot, so it outlasts the log line.
  - **KRN-03 PCIe bus errors:** WARN on any fatal or non-fatal AER count summed across devices; correctable counts are shown for context only, as that counter only grows. No AER counters (firmware-first) reads NOT CHECKED, never a pass.
  - **NET-17 bond timing:** WARN on slow-failover bond settings (LACP rate slow on 802.3ad, no link monitoring, or a balance-rr/xor/tlb/alb mode), since a bond slower than the corosync token can cost cluster membership on a cable fault.
  - **NET-18 link flap:** WARN when a NIC's carrier changes per hour since boot exceed the new `linkFlapWarnPerHour` site standard (default 5). A rate since boot, so a short recent burst on a long-running host is diluted.
  - **NET-19 bridge VLAN filtering (2.0):** a VLAN-aware bridge with filtering on passes; a per-VLAN bridge, whose name carries the VLAN (e.g. `hvmbr0.60`), with filtering off is read for information only, as it isolates by being one bridge for one VLAN; a bridge whose name does not carry a VLAN and has filtering off WARNs, as it may carry several. A real 2.0 host used per-VLAN bridges, so confirm the intended model with HPE.
- **HW-02 reworded:** a zero EDAC count is no longer read as proof of healthy DIMMs, because an HPE firmware-first server can hide corrected errors from Linux; the PASS text and action now say to read the management controller too. The FAIL/WARN logic is unchanged.
- **HST-08 root-filesystem coverage confirmed:** `/`, `/var`, `/var/log`, `/tmp` and `/boot` are read by explicit path, deduplicated by device, and never with a bare `df`, which would block on a frozen GFS2.

**Alarms, who they reach, and planned work**
- **One alarm per incident.** A freeze used to raise a dozen alarms. Now a cause (DLM-01, CLU-03, GFS-01) raises one, naming the hosts and the findings it explains, and the same check on several hosts is one alarm, on the cluster. The tab still lists every finding, grouped. Findings with their own action stand alone, including everything that always pages. When the cause clears, what is left stands on its own at the next run.
- **Acknowledgements last longer.** An alarm's identity is now the check, not the host, so it survives hosts coming and going. It is raised again when the check reaches a host it does not name, because an acknowledgement of the old hosts must not hide that. Upgrading replaces open per-host alarms with their groups once, so those acknowledgements are lost that one time; a cluster-wide alarm keeps its own.
- **An alarm naming a host that did not answer stays** until the host answers, rather than clearing and coming back with no acknowledgement.
- **An alarm raised again keeps its start,** and says it had been acknowledged and by whom, so that is not simply lost when a check reaches a new host or changes severity.
- **A symptom that appears later gets into the alarm's text,** as long as nobody has acknowledged the alarm.
- **What a run could not read keeps its alarm:** an isolation alarm whose host answered with its ports unread, and an alarm only a full check can judge when none has run since the load. So a freeze found ahead of the first full check no longer clears those until the next turn.
- **A full check that could not read something keeps what it last found there,** as last read, on the tab too: the full-only findings of a host that did not answer, and a failing disk behind a controller when the disks ran out of time. They used to clear until the next full check, a day away.
- **Who a finding reaches**, in the tab and the alarm: `affects 14 running VMs in 3 tenants: A (9), B (4), C (1)`, with operator VMs counted apart. A datastore finding counts VMs with a disk there. What was not read is never "none": VMs on a silent host have a state not known, and a disk Morpheus does not place is counted as such. None of this goes in a report.
- **Change windows.** Start and End on the tab, with a reason and a required length, at most the new Longest change window setting (24 hours). A window holds paging only: checks, alarms and history carry on, freezes, withdrawn filesystems and isolation failures still page, and it ends by itself. It survives a reload, is audited, and shows on the tab and the all-clusters page.
- **Busiest VMs** panel on the tab, when a check has read them.
- **Listing alarms no longer grows with the square of the clusters:** each cluster lists its own, once Morpheus has shown it answers the filter correctly.

**Across clusters and over time**
- **Possible shared cause (FLT-01):** the same finding appearing on two or more clusters within 10 minutes when they share an iSCSI portal, a time server or a group in the new **Shared risk groups** setting, or on three or more whatever they share. Shown on the all-clusters page and as one alarm on the master tenant, never on a cluster's tab, as it names other clusters. Only a finding's arrival counts, so one open for months across many clusters raises nothing. A cluster in a change window does not count, and neither does what first appeared during its window, so rolling work raises nothing. A confirmed isolation failure (NET-12, NET-13 at FAIL) still counts, as no window holds those. Their first, confirming, sighting is only a warning, which a window holds.
- **One failure from an outage:** a section of the all-clusters page, built from existing findings, with the reasons and no score: no quorum margin, no N+1, the manager on the cluster, an old agent, a degraded redundant path.
- **Capacity forecasts:** one sample a day per cluster for up to 90 days, in its own row. **CAP-03** N+1 memory and **GFS-11** a datastore reaching `gfs2FailPct`, within the new `forecastWarnDays`. With under 14 daily samples they are not checked, never a pass. A frozen or silent morning leaves a gap, not a dip.
- **CAP-02:** vCPUs of running VMs against host threads, with `vcpuWarnRatio` and `vcpuFailRatio`. A running VM with no vCPU count, or a host that did not answer, is not checked.
- **STO-07:** the array's warning that a thin LUN crossed its soft limit, from the kernel log on full checks.
- **A second crash of one VM counts.** A stop now counts by its own time, so a VM that crashes again inside VM-06's 24 h adds to the availability figures, and a tenant's list says when it stopped rather than when the check saw it.
- **Availability figures:** freeze time, stalls and unplanned VM stops by month, per cluster and per tenant, on the tab and the all-clusters page. A freeze is written when it starts, so a reload does not lose it. A period with no checks is shown as unknown, never as up. A per-tenant CSV holds only that tenant's own data, to hand to that customer.

**HPE's own checks and disks behind a RAID controller**
- **HPE-01:** on 2.0 hosts, a full check also runs `hvmcli health check --json`, as a time-limited background read and only with DLM healthy, as it may read GFS2. The Hosts section shows every answer per host, marking the four that read Pacemaker, which HVM masks, and these raise nothing. HPE-01 warns when any check outside the new `hvmcliIgnore` standard says WARN or FAIL, and never fails, as these are HPE's thresholds. No hvmcli on a 2.0 host, or output that will not parse, is NOT CHECKED. HPE's details stay in the panel, out of alarms and reports.
- **HW-07 reads physical disks behind a MegaRAID controller:** on full checks, each gets its own result naming its slot, up to 24 within 40 s. Only the scan's `megaraid` entries are read, never an iSCSI LUN. A RAID volume says which physical disks were read instead, when they are on its own controller.
- **HW-07 fails on a WHEN_FAILED value other than a dash,** on a boot disk as on a disk behind the controller. This includes `In_the_past`.
- **A full probe's order:** the thin log, VM ports and busiest VMs now come before the disks behind a controller and HPE's check, so running short costs those two, which say so, and not the others. Disks are read in a section of their own.
- **HCI Ceph only when the code says so.** A 1.3 layout is read as HCI Ceph only if `hci` or `ceph` is a word of its code. Any other 1.3 code used to count too, which skipped the freeze watch and the DLM and GFS2 checks on a real GFS2 cluster with such a code. It now gets them.

**Agent quorum, the authority on 1.3 and 2.0**
- **CLU-14 Agent quorum achieved.** Every check now reads HPE's agent quorum endpoint `https://127.0.0.1:7443/quorum` (on the host over HTTPS to localhost, never a GFS2 path, so safe). FAIL when quorum is not achieved or this host is fenced; WARN when a node is being fenced or is unreachable to the agent; NOT CHECKED when the endpoint gives nothing or not the documented JSON. HPE states this, not corosync, decides quorum on 1.3 and 2.0, so CLU-03 only corroborates it. Built from HPE docs, the payload shape only partly known, and not yet seen on a real two-host or stretch cluster.
- **CLU-15 Agent, corosync and Morpheus list the same members.** Compares the members the agent lists (`/quorum` and `/opt/morpheus-node/.quorum-nodes`) with the corosync nodelist and Morpheus's hosts. A node corosync counts but the agent does not is the precondition suspected behind the production freeze: read only, no fix, as HPE says not to hand-edit these files. The file format is undocumented, so an identifier scheme it cannot read is NOT CHECKED rather than failed.
- **CLU-03 and CLU-04 re-aimed.** HPE says corosync Quorate does not decide on 1.3 and 2.0 and reads No on a healthy two-node cluster. So on a genuine two-node corosync cluster (expected votes 2) both are now informational (NA) and point to CLU-14, and a two-host cluster's missing vote margin is no longer a failure. A degraded cluster of three or more still reads corosync as before, with a note that the agent decides. Stretch is not told apart from single-site, so a healthy stretch cluster may still read FAIL there; CLU-14 is authoritative.
- **CLU-12 reworded.** HVM's two-node witness is a Distributed Worker reached over HTTPS and part of the agent quorum, not a corosync qdevice, so the check stays NA in normal HVM use and only judges a real corosync qdevice where one is configured.
- **MIG-02 adds TCP 7443.** The full check now tests both TCP 22 (hosts migrate over SSH) and TCP 7443 (the agent's heartbeat and quorum pings) to every peer, naming the port that is closed. A peer from an older probe with no 7443 result is judged on 22 alone.

**GFS2 and DLM freeze detection, from source reading**
- **GFS-10 matches more withdrawal wordings.** The 7-day kernel-log search is now case-insensitive and adds `about to withdraw`, `file system withdrawn`, the `fatal:` messages and `lvb ... mismatch` to the fsid line. The wordings are read from GFS2 source, not yet seen against a real log, so a withdrawal worded otherwise could still be missed.
- **DLM-03 can fail, and names the wait state.** A stopped lockspace that no fence wait, inferred wait or split state explains is now a failure, with the wait state from `dlm_tool ls` (ringid, quorum, messages, fsdone) in its hint. It also reads `lock_module/block` (a safe read, folded into FS_SAFE) and warns when locking is blocked with nothing stopped in `dlm_tool ls` — a single sighting, as the checker has one snapshot.
- **DLM-07, the `-125` split state.** A new check for the freeze a hand-run `dlm_tool fence_ack` cannot clear (it is refused with -125, no need_fencing): it names the state, offers no acknowledgement, and says the way out is a clean rejoin of the node. From dlm source and one 27-minute production run, not reproduced; 2.0 unconfirmed.
- **DLM-06 reworded as a latent freeze.** A fence line with lockspaces running blocks the next membership change, so it is not harmless; the text now says to do no host work until it clears, and that a fence result of 177 means no fence agent is loaded, not a fence that failed.
- **KRN-04 kernel floor and KRN-05 `-22` defect.** KRN-04 warns when the running kernel is below the per-layout `minKernel` floor that carries the DLM/GFS2 freeze fixes, and says which fixes 6.8 still lacks even above it. KRN-05 fails on HPE's `validate_lock_args -22`/`lm_lock ret -22` signature since boot, with HPE's recovery procedure. Both are read from the Ubuntu changelog, kernel source and HPE's note, not seen on a host here.
- **Hung-unmount advice.** Removal advice (Preflight, HostOps) no longer says to reboot to clear a hung unmount: source shows the kernel's wait is bounded at about 600 s and then leaves cleanly, so it says to wait out Morpheus's own timeout and reboot only once the host is certainly out of use. The 600 s self-clear needs one test run to confirm.
- The 2.0 journal-replay gap (a withdrawn node's journal may not replay until it remounts) is noted in GFS-02 and GFS-06 and the backlog; no check is built on it.

**Vendor-neutral storage**
- **STO-01 standby paths.** An ALUA standby path (checker `ghost`, as Alletra, Nimble and Peer Persistence legs report) is healthy standby, not a fault. It used to raise a permanent false failure on any array with standby paths. 0 paths and a map with no active path at all (only standby left) still fail; the standby count is shown.
- **STO-02 is now the no_path_retry window, reported in seconds** (`retry x polling + 1`) and never a failure. It warns only when the window is under the corosync token, or over the new `noPathRetryPolicy` ceiling (180 s). Two misreads are fixed: `N sec` means the map has no path at that moment (a countdown), and `off` with no active path means the retries are exhausted; both used to read PASS. The vendor's documented value is shown, from a profile built from documentation.
- **Fibre Channel.** The probe reads `/sys/class/fc_host` and `fc_remote_ports`, and per-path transport from multipathd `%P`. **STO-03** is NOT CHECKED on an FC-only host, rather than a quiet pass on an iSCSI error count that says nothing. **STO-04** (renamed Storage path daemons) judges multipathd wherever maps exist, FC included, and iscsid only where there are iSCSI sessions. The **STO-01 fix** rescans by transport, never an iSCSI rescan on an FC host. **STO-09** is a new FC fabric check (ports Online, a remote target up, two adapters), built from documentation as the test hosts are iSCSI.
- **STO-08:** the array's trimmed INQUIRY vendor and product map to a vendor family and name the transport; an unknown vendor is NOT CHECKED, so a vendor-specific rule never judges it. Pure-specific tuning stays in the Pure plugin.
- **STO-10:** iSCSI `node.startup` not automatic warns, as a rebooted host returns with no session. **STO-11:** each session's live `recovery_tmo` against multipathd's `fast_io_fail_tmo` (120 s meaning never applied), the vendor's documented value (labelled unverified), and across hosts. **STO-12:** paths per LUN below the new `expectedPaths` site standard, the absolute floor STO-05's cross-host compare misses.
- **STO-07** now also fails on a hard space-allocation failure (SCSI sense 27/07 DATA PROTECT, "critical space allocation") or a write-protected map, not only the soft-threshold warning. **STO-13:** a map that lost every path in the multipathd log over 7 days, the near-miss before an all-paths-down outage (full check only).
- **24.04 vs 26.04:** multipathd's `%A` (target port group) and `%k` are read only on 26.04 (0.14.3); on 24.04 that detail reads as not read rather than erroring.

**Tenant isolation and side channels (full checks only)**
- **SEC-01 nested-virtualization exposure.** WARN when a customer VM presents VMX (Intel) or SVM (AMD) to its guest, read from the VM's effective CPU block in its domain XML. The gate is the host's kvm nested parameter, not the per-VM "Enable Nested Virtualization" box and not a role: host-passthrough exposes it only when the host has nesting on and no feature disables it, and a named model exposes it only when it requires it. A named model with VMX/SVM disabled is not a finding. Alarm named `SECURITY:`, operators only, never in a report. Built from HPE docs and one hand-edited VM, not seen as a Morpheus default.
- **SEC-02 kernel escape-fix level.** Compares the running kernel against `kernelCveMin`, pinned per layout to the Ubuntu fix level for the 2026 KVM guest-to-host escapes (Januscape, Zapscape), by upstream version and ABI, not just the dotted version. FAIL below it where nesting is exposed, WARN below it where it is off, NOT CHECKED when the layout has no fixed version set or the kernel cannot be read. The text says to ask HPE, as the ABI is unverified against HPE's build and a FAIL with no published kernel cannot be patched away.
- **SEC-03 CPU side-channel mitigations,** a note, detection only, no exploit: lists any `/sys/devices/system/cpu/vulnerabilities/*` the kernel marks Vulnerable, and the SMT state. HPE owns the kernel, microcode and SMT, so it raises nothing.
- **SEC-04 2.0 bridge STP,** a note: the STP state of each VLAN-filtering Linux bridge, to raise with HPE. STP on lets a guest take the bridge root; STP off lets guest BPDUs reach the uplink, where BPDU guard can err-disable the trunk. HPE documents neither.
- **SEC-05 customer VM on an infrastructure VLAN.** WARN when a customer VM port's VLAN matches a VLAN the host's cluster or storage interface is tagged with. The storage VLAN is the dangerous one: a guest there could try to reach the LUN that holds every tenant's disks. No row where no infrastructure interface is tagged, so there is nothing to compare. Operators only, never in a report. Built from documentation.
- **SEC-06 per-VM resource limits,** one fleet note: how many running customer VMs have any per-VM I/O, CPU or network limit in their domain XML, which today is none. Morpheus documents almost no such limit, so fairness rests on the array and the host. Never one alarm per VM.
- **VM-07 cache=unsafe.** FAIL when a VM disk uses `cache=unsafe`, which drops the guest's flushes so a host crash can lose acknowledged writes: the one cache mode that is wrong on a clustered datastore. The other modes are left alone.
- **NET-12 and NET-13 now report macvtap (Private) and SR-IOV ports as NOT CHECKED,** rather than reading a macvtap port as a bridge port with no master or skipping an SR-IOV hostdev port entirely. Neither sits on a readable bridge.
- **The probe hardens against tenant-chosen VM names.** A name reaches `|`-delimited, `@@`-sectioned probe output, so the probe now strips control characters and turns `|` into `_` in names before they become fields, and the parser treats only an exact `@@<lowercase token>` as a section marker, so a crafted name cannot shift another field or forge a section. Surfaced names are scrubbed of control characters and length-capped.
- **The report withholds by allow-list, not deny-list.** A finding's observation is carried only when its check is known to name only hosts, storage, configuration and numbers; everything else, a new check included, is withheld, so an unknown name cannot leak. Scrubbing known names stays on top, and the report still fails rather than leak if those names cannot be read.
- **HPE's numbers where a threshold was a guess.** `vcpuWarnRatio`/`vcpuFailRatio` (4, 8) and `gfs2WarnPct`/`gfs2FailPct` (80, 90) are now sourced `hpe`, matching HPE's capacity table (2:1 general, 4:1 dev/test, 8:1+ with caution) and documented datastore alarms (80/90). Host CPU and memory utilization alarms (85/95, 90/95) stay HPE's own; the plugin's HST-06/HST-07 measure pressure, which complements them rather than repeating them. HPE's 4 GB host memory reserve is not yet subtracted in CAP-01 (see BACKLOG).

**Known-defect and advisory checks (from the release-note and failure-mode research)**
- **HB-02 all-paths-down shutdown.** A full check searches the host journal over 7 days for the agent's APD VM shutdown — the "Shutting down all VMs to protect data integrity" line and the "heartbeat datastore paths ... unhealthy ... for N checks" precursor — and FAILs on any sighting, the biggest outage the plugin did not detect. A journal it cannot read in time is NOT CHECKED, never a pass. The exact agent wording and the destroy timer under path loss are unverified, so it is built from documentation and the one real line; see [docs/HPE-QUESTIONS.md](docs/HPE-QUESTIONS.md).
- **FEN-02 SCSI fence-agent defect.** Advisory a00156214: a cluster created on Manager 8.0.11 or 8.0.12 powers off every surviving VM when one host fails. The plugin cannot read a cluster's creation version, so a full check warns when the Pacemaker-era agent `/usr/sbin/fence_scsi_hpevm` is still present on a 1.3/2.0 host, and points to the hotfix or a layout upgrade through HPE. Built from documentation; it never offers the hand edit as a fix.
- **CLU-16 stale rejoined config_version.** Sharpens CLU-06: warns when a host's corosync.conf config_version is below the others, which a host down during an add or remove returns with, and which can leave a ghost CPG member that hangs the cluster until corosync restarts everywhere. Built from corosync source and a Proxmox reproduction, not seen on HVM. Read from the file every host already reports, so no new probe read.
- **PKG-03 softened.** Still flags agents below `agentMinVersion`, but the advice now says to upgrade in a maintenance window, one host at a time, as an agent upgrade has itself triggered failover outside maintenance (HPE fixed one case in 8.0.13-2).
- **PKG-01 softened.** It no longer recommends a patching method, because HPE's own 9.1 docs disagree on whether `apt upgrade` is allowed on an HVM host; it points to HPE's rolling update and documented procedure instead.
- **GFS-06 reworded.** Morpheus runs `gfs2_jadd` itself when it adds a host, so too few journals usually means that step did not finish rather than something to add by hand.
- **docs/HPE-QUESTIONS.md.** One question per check-default this release has to guess, publishable and naming no site: the APD wording and timer, the fence-agent creation version, the corosync ghost-member backport, the patching conflict, agent-upgrade safety and journals.
- **Quiet on Ceph confirmed.** HB-02 and FEN-02 skip an HCI Ceph cluster, as the DLM, GFS2, heartbeat and thin-LUN checks already do.

## 0.3.0

The first release tested against live HVM 1.3 and 2.0 clusters, including real freezes.

**Removing a host**
- **Remove safely replaces safe eject,** whose `enableEject` setting is gone. Morpheus's remove is a clean leave when all goes well, but it carries on when GFS2 will not unmount. So the plugin checks what that remove does not (nothing has GFS2 open, no VMs on record, quorum kept, no host recovering), unmounts GFS2 itself with a time limit, stops there if that hangs, and only then calls Morpheus's remove and watches the remaining hosts.

**New checks**
- **Failover (HA-03, HA-04, HA-05):** the cluster's "Automatically Power On VMs", which decides whether a lost host's VMs restart, the cloud's for reference, and a heartbeat target.
- **GFS-10:** consistency errors and withdrawals in the kernel log over 7 days, because a reboot clears the live state and the agent reboots a host soon after a withdrawal.
- **Tenant network isolation (NET-12, NET-13):** VM ports against their Morpheus VLAN, and trunks, with `trunkAllowedVms`. On 1.3, a customer VM on a network with a blank VLAN or VLAN 0 has a port with no tag, and a guest there reached a guest on a tagged VLAN by tagging its traffic. Critical when another tenant's VLAN is reached.
- **NET-15:** iSCSI on physical ports of its own, traced under VLANs, bonds and bridges. NET-02 compares only interface names, which can sit on one bond. Where sharing is deliberate, list it in `disabledChecks`.
- **MIG-07:** VMs that cannot live-migrate because of their CPU settings, which the pre-flight now says too. **MIG-06:** VMs still on host-passthrough under a named cluster CPU model.
- **DLM-06:** `dlm_controld` still retrying a fence with every lockspace running. This used to read as a freeze, and offer an acknowledgement.
- **PKG-03:** the Morpheus agent older than 4.0.1. Agent 3.2.6 acknowledged the wrong nodes in a real freeze, while newer agents acknowledged correctly in every test. Set `agentMinVersion` to change it.
- **HA-06:** the Morpheus manager running on the cluster it manages, where a freeze takes the console and every alarm with it.
- **NET-16:** a cluster network address from DHCP. A lost or changed lease takes a host out of the cluster.
- **MOR-05:** an error in Morpheus's status for a host that looks healthy. **MOR-06:** a cluster record marked failed, usually an add whose last steps failed.
- **CLU-13:** an empty corosync authkey. An add can fail partway and still show the host as provisioned, leaving the others a vote short. `rejoin` is no longer offered on such a host, as deleting and adding it again is what works.
- **Morpheus's own Remove** is called out in HA-02 and CLU-05, as its checks do not run through there. **DLM-01** shows the time before HVM's agent starts stopping VMs.
- **PRB-03:** a mistake in the site standards warns, and checks carry on with the built-in ones. **PRB-02:** an automatic check that could not run at all.
- **Quorum device (CLU-12), certificates (HST-02, HST-03), boot disks (HW-07), storage migration space (GFS-09), frame size (NET-14).**

- **A freeze with no fence line** is named too: DLM-01 works out the node from the lockspace's members, and the emergency plan offers it. A delete during a GFS2 mount froze a test cluster this way for 27 minutes, with no finding at all. Remove safely now also holds back a host that joined under 10 minutes ago.
- **GFS-10** is critical for an error since the host's last boot, and a warning afterwards, for up to 7 days.

**Pages and history**
- **A reference for every finding.** Each check id in the readiness and findings tables opens a popup with what it looks at, why it matters and what to do, and **Help**, beside Run full check, searches all of them by id or words and explains the statuses and id prefixes. The text is written from the code and comes from one place, `CheckCatalog`, through a new read route with the same gate as `status`. [docs/CHECKS.md](docs/CHECKS.md) is generated from it, and tests fail if an id, a standards key or that file falls out of step. The report keeps its ids as plain text.
- **All-clusters page** under Operations > Analytics > Cluster Health, for the master tenant only, replacing the section at the top of the cluster tab.
- **Finding history:** when each finding first appeared and cleared, kept across plugin reloads, and shown as First seen. Cleared findings are kept for a year, up to 500 per cluster. No observed text, raw output, or tenant, VM or network names are stored.
- **Cluster report:** current findings and their history, to print or export as CSV or JSON. Generating one is audited. It holds no tenant data; see docs/PERMISSIONS.md.

**Fixes from running on live clusters**
- **Frozen** now requires a stopped lockspace, not just a fence line, and the emergency plan accepts a host restarted into a stopped lockspace.
- **The pre-flight** answers within 90 s on a silent host, rather than a 504 from the proxy.
- **Heartbeats** are matched on the host's name as well as its system hostname, which changes on a re-add.
- **All-clusters order** counts failures and warnings within a health level. **A journal count of 0** is a failed read, not a finding.

- **Time on systemd-timesyncd:** the time view, offset, drift and source checks now read timesyncd, which is what a Morpheus-built 1.3 host runs. Synced hosts no longer show "none configured: following nothing".
- **Drift** compares only hosts reading the same server, by address, and says what is left unknown when they read different members of a pool. Timesyncd reports one sample per host, so what it shows warns rather than fails.
- **`ntp-sources` on timesyncd:** a drop-in in `/etc/systemd/timesyncd.conf.d/`, a restart and a check that a listed server answers, putting the previous configuration back if none does. Same maintenance-mode guard.
- **STO-02** reads `multipathd show maps format '%n %Q'`. Only "on" is the finding: a finite retry such as `12 chk` was a false alarm. Without that value it says it cannot tell, rather than claiming endless queueing from the dm features line.
- **New status, not checked:** a check that applies but could not be answered. A missing `ipmitool` now reads "cannot tell: ipmitool not installed" on FEN-01, HW-01, HW-03 and HW-04, not "none", and readiness shows it.
- **VLAN test:** without `arping` it says "arping not installed: not tested" before anything moves. An arping that gives no result is not tested, never a pass or a VLAN failing. It tests every active-backup bond on a bridge and names the bond in each result, and silence on one bond is only a failure if none answers. A bridge it cannot test is reported, and a VLAN silent on the rest is inconclusive. Its timer and the plugin's wait now scale with bonds and VLANs.
- **PKG-01** compares the Morpheus agent's version from `/opt/morpheus-node`, as it is not a dpkg package there, and says not checked when it cannot read one.
- **LAY-05** no longer shows a trailing comma.
- **HA-01** is a note, not a warning: `notHighAvailability` is set on every cluster seen so far and its meaning is unknown.
- **`service-enable`** had its tier inverted, which hid the button. **NTP turned off** now reads as a finding with its fix while the clock still says synchronised, since the kernel keeps saying so long afterwards.
- **A record Morpheus is still removing is not a host:** it blocked every fix. It now gets its own warning, MOR-04.
- **A silent host names the VMs recorded on it**, rather than "no running VMs". `rejoin` says that it does not mount GFS2, and to reboot in maintenance mode: leaving it without that can make the agent force a reboot.
- **Corrected what a lost host does**, from measurements: HVM's agent normally acknowledges within about 2 minutes, and if nothing does, the agent stops VMs at about 9 minutes.
- **New setting, Clusters automatic fixes apply to** (`autoFixClusters`): ids or names, comma separated. Empty means none, so **automatic fixes that were on stop until a cluster is named**. Checked again on fresh state and the settings as saved, when a fix runs.

**Fixes from auditing the release candidate**
- **Routes that change something answer POST only.** Fixes, the time source, VLAN tests, Remove safely and the acknowledgement ran on a GET, which has no CSRF token, so a link could trigger them.
- **The emergency panel and raw output answer within 90 s,** before the proxy's 504, as the pre-flight already did.
- **A slow probe no longer hides a freeze.** The probe reads DLM and quorum first, and stops reading at a limit it is told, 30 s before the caller gives up, then says it was cut. A host cut short gets PRB-01 and still names the freeze; for everything else, fixes above all, it has not answered.
- **GFS2 guard:** every mounted filesystem needs a lockspace listed, as an empty list after `dlm_controld` restarts is not healthy. `gfs2_edit` and reading process arguments, which can sleep unkillably, run in a job the probe stops waiting for.
- **The VLAN test cannot cost a host its membership.** VLANs go in runs of at most half the corosync token on any uplink (3 at 60 s), with the uplink back between them. A lock on the host refuses a retry while a test or its timer runs, and the test prints the uplink it found and fails if it did not get back there.
- **A refusal gives nothing away.** It goes to the appliance's log, not an audit entry in the caller's tenant, and a missing cluster answers 403 like someone else's.
- **Report and history:** tenants that own a network here are withheld, a network read that fails fails the report, and MIG-06, MIG-07, NET-12 and NET-13 lose their observed text. History no longer stores the VM name in the NET-12 and NET-13 titles.
- **Monitoring:** a check that cannot run, such as with a typo in the site standards, raises an alarm (PRB-02), leaves the others as they were and waits the normal interval. Four clusters are checked at once, so silent hosts on one do not delay the rest. Site standards of the wrong type are refused by name.
- **Alarms** are no longer replaced when only their text changes, which lost acknowledgements and start times. A finding that could not be judged keeps its alarm. Those of a deleted cluster, or of any cluster with automatic checks off, clear daily.
- **Failures no longer read as healthy:** an unread kernel log is not "no GFS2 errors" (GFS-10), vanished paths count, and a map with none fails (STO-01).
- **Alarms on healthy clusters:** HB-01 leaves stale files to HA-03 when every host has them, reads a host's newest file, and does not judge a host just added back on a file from before it joined. STO-06 needs 20 I/Os. HW-05 compares within a bond. NET-10 ignores a /32 VIP inside a host's own subnet. NET-11 is not checked rather than a warning, as it comes and goes with traffic. DLM-02 waits for the agent's usual 3 minutes.
- **NET-15** read not checked on real clusters: the ring addresses reached `awk` across several lines, so the ring device got no ports.
- **`ntp-enable` needs maintenance mode,** as it can step a clock. **An unmount refused** starts its pool again, and says so. **A fence acknowledgement** only reports recovery from a `dlm_tool` that answered. **The pre-flight** sizes VMs together, not each alone. **Removal stopped after the unmount** says GFS2 is unmounted and to reboot in maintenance first. **The time source** is not saved when the cluster is busy. Automatic retries are per cluster.
- **Removed:** the optional VLAN and gateway on the VLAN test, the tab's opener by URL, and `quorumFencing`, which nothing checked.

## 0.1.2

First release. Cluster Health tab for HVM 1.3 and 2.0 clusters.

- Read-only probe through the Morpheus agent that never touches a frozen GFS2 mount.
- Checks across hosts: membership and quorum margin, DLM fence waits and agent acknowledgements, GFS2, heartbeats, VMs, multipath,
  network, netmask drift, LLDP neighbours, time, live and storage migration readiness, N+1 capacity, and Morpheus's view against the hosts'.

- Fixes in three tiers (safe, maintenance, emergency) with guards evaluated on fresh state, automatic fixes off by default.

- Operators only: master tenant and the cluster's owner; customers are refused.
